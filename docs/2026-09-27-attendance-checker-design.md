## 0. 이어받는 AI에게 (먼저 읽기)

- **학습자:** 서버·리눅스 입문자. AX팀 소속, RPA 경력. 자세한 성향은 `PROGRESS.md`의 "학습자 정보"를 볼 것.
- **지금 할 일:** 아래 6장 **설계 4**를 사용자에게 제시 → 승인 → 이 문서를 "확정본"으로 갱신(셀프 리뷰 포함) → 사용자 검토 → 작업 계획(단계별 체크리스트) → 구현.
- **진행 규칙:**
  - 설계는 **한 조각씩** 보여주고, 사용자가 OK하면 다음으로 넘어간다.
  - 질문은 **한 번에 하나**. 가능하면 객관식.
  - **승인 전에는 코드 작성·폴더 생성·저장소 생성 금지.**
  - 구현은 **사용자가 직접 타이핑**하는 실습으로 한다. 어느 창(PowerShell / WSL 우분투 / AWS 서버)에서 치는지 매번 표시한다.
- **설명 방식:** 짧고 literal하게. 비유는 사용자가 아는 것(윈도우, 회사 업무, SQL 경험)에 빗댄다. 추상 비유(붕어빵 등)는 역효과였다. 사용자가 이해한 걸 말로 정리하고 "맞아?"라고 물으면 **먼저 맞다/틀리다를 말하고**, 사용자 표현 그대로 짧게 재확인한다.

## 3. 설계 1 — 전체 구조 ✅ 승인

### 파일 구성 (파일마다 역할 하나)

| 파일 | 하는 일 |
|---|---|
| `answers.py` | 심을 **정답 목록**. 사람이 손으로 직접 적는다 |
| `seed.py` | 가짜 데이터 생성. **실행할 때마다 DB를 지우고 새로** 만든다. 정상 데이터는 **규칙적으로** 만들고, `answers.py`의 정답을 심는다 |
| `attendance.db` | SQLite DB 파일. `seed.py`가 만든다. **Git에 안 올린다** |
| `checks.py` | 이상 기록을 찾는 SQL 규칙. 함수가 **검사할 DB 연결을 받아서** 쓴다. 맨 위에 기준값 `TIME_DIFF_MINUTES = 10` |
| `app.py` + `templates/index.html` | 결과를 웹 화면으로 보여준다 (Flask + 템플릿) |
| `test_checks.py` | **테스트용 DB를 새로 만들어서** 검사한다. **누락 0, 오탐 0**이어야 통과 |
| `Dockerfile` | 이미지를 만들 때 **`seed.py`도 실행**해서 DB를 이미지 안에 넣는다 |
| `requirements.txt` | 파이썬 의존성 |
| `.gitignore` | `attendance.db`, `venv/`, `__pycache__/`, **`*.csv`, `*.xlsx`** (실데이터 실수 방지) |
| `README.md` | 매 작업 단계 끝마다 갱신 (사용자 규칙) |
| (도구) `sqlite3` | SQL을 코드에 넣기 전에 **손으로 먼저 쳐보는** 용도 (`sudo apt install -y sqlite3`) |

```
    │                          │
seed.py ─▶ attendance.db      test_checks.py
 (매번 새로)     │                  │ 테스트용 DB를 새로 만들어서
            checks.py ◀────────────┘ "찾은 것 = 정답?" 확인
                │
            app.py ─▶ 웹 화면
```

### 셀프 리뷰로 추가된 원칙 (사용자 요청으로 검토함)

1. `seed.py`를 두 번 돌려도 데이터가 쌓이지 않게 **매번 새로** 만든다. (안 그러면 가짜 "중복 기록"이 생긴다. W5의 "중복 적재"와 같은 사고)
2. 정상 데이터는 **기준(10분)을 절대 못 넘는 범위** 안에서 규칙적으로 만든다. 제한 없는 무작위는 우연히 이상 기록을 만들어 테스트를 불안정하게 한다.
3. 정답은 판정 규칙과 **독립적으로 손으로** 적는다. 규칙으로 정답을 계산하면 규칙이 틀려도 테스트가 통과해버린다.
4. Docker 이미지를 만들 때 `seed.py`를 실행해서 DB를 넣는다.
5. `checks.py` 함수는 DB 연결을 받아서 쓴다. 앱은 진짜 DB, 테스트는 새 테스트용 DB를 넘긴다.
6. `sqlite3`로 SQL을 손으로 먼저 쳐본다.
7. `.gitignore`로 실데이터(`*.csv`, `*.xlsx`)가 Git에 올라가는 걸 막는다.

**검토했지만 그대로 둔 것:** SQL을 `.sql` 파일로 분리(파일만 늘어남), 사번↔단말 ID 연결 표(W4의 실제 문제지만 첫 버전엔 과함 → 확장 후보), `templates` 폴더(페이지는 하나지만 Flask 표준이라 유지)

## 4. 설계 2 — 데이터 ✅ 승인

### 표 3개

**`employees` (직원 목록)**
| 컬럼 | 설명 | 예 |
|---|---|---|
| `emp_id` | 직원 번호 | `E001` |
| `name` | 가짜 이름 | `직원01` |

**`terminal_logs` (단말 출입 기록 = 회사의 캡스 출입기록 역할)**
| 컬럼 | 설명 | 예 |
|---|---|---|
| `id` | 줄 번호 (자동) | `1` |
| `emp_id` | 직원 번호 | `E001` |
| `work_date` | 날짜 | `2026-09-02` |
| `log_time` | 시각 | `08:02` |
| `direction` | `IN` 또는 `OUT` | `IN` |

**`manual_sheet` (수기 시트 = 회사의 근태일보·시트 역할)**
| 컬럼 | 설명 | 예 |
|---|---|---|
| `emp_id` | 직원 번호 | `E001` |
| `work_date` | 날짜 | `2026-09-02` |
| `check_in` | 수기 출근 | `08:00` |
| `check_out` | 수기 퇴근 | `17:00` |

**형식 규칙:** 날짜는 `YYYY-MM-DD`, 시각은 **항상 두 자리 `HH:MM`**(예: `08:02`). SQLite는 날짜·시각을 글자로 저장하는데, 두 자리로 맞춰야 글자 비교(`MIN`/`MAX`)로도 순서가 맞다.

### 정상 데이터 규칙

| 항목 | 규칙 |
|---|---|
| 직원 | 10명 (`E001`~`E010`, 이름 `직원01`~`직원10`) |
| 날짜 | 평일 10일: 2026-09-01, 02, 03, 04, 07, 08, 09, 10, 11, 14 |
| 수기 시트 | 전원 매일 출근 `08:00` / 퇴근 `17:00` (점심·흡연은 안 적음) |
| 단말 — 모든 직원 매일 | `08:00 IN`(출근) → `12:00 OUT`(점심) → `13:00 IN`(복귀) → `17:00 OUT`(퇴근) |
| 단말 — 짝수 직원 추가 | `E002, E004, E006, E008, E010`은 매일 `15:00 OUT` → `15:10 IN` (흡연·화장실) |
| 흔들림 | 단말 시각은 위 기준 **± 0~3분** 안에서만. **매번 똑같은 결과**가 나오게 만든다 |

> 이 규칙은 사용자 지적으로 추가됐다: 실제 출입 기록은 점심·흡연·화장실 때문에 하루에도 여러 번 찍힌다.

## 5. 설계 3 — 찾기 규칙 + 결과 화면 ✅ 승인

### 기준 (사용자가 실무 방식을 확인해줌, 2026-09-27)

| | 등록되는 시각 |
|---|---|
| 출근 | 그날 **첫 기록** (IN이든 OUT이든) |
| 퇴근 | 그날 **마지막 기록** (IN이든 OUT이든) |

실무에서는 퇴근을 안 찍으면 **마지막으로 찍은 시각이 퇴근으로 등록**되고, 출근을 안 찍으면 **첫 기록이 출근으로 등록**된다. 그래서 미태그는 근무시간이 짧게 잡히는 급여 문제로 이어진다.

### 찾기 규칙 (만드는 순서대로)

| 순서 | 종류(표시 이름) | 정의 | 정답 | 배우는 SQL |
|---|---|---|---|---|
| ① | 중복 기록 | 같은 직원·날짜·시각·방향 기록이 2개 이상 | 2건 | `GROUP BY`, `HAVING`, `COUNT` |
| ② | 기록 없음 | 수기 시트엔 그날 줄이 있는데 단말 기록이 0건 | 2건 | `NOT EXISTS` (두 표 대조) |
| ③ | 출근 미태그 | 그날 **첫 기록이 OUT** | 2건 | 묶음별 첫/마지막 값 찾기 (`MIN`/`MAX` + 서브쿼리 + `JOIN`) |
| ③ | 퇴근 미태그 | 그날 **마지막 기록이 IN** | 3건 | 〃 |
| ④ | 시각 어긋남(출근) | 첫 기록 시각과 수기 출근의 차이가 **10분 이상**. **출근 미태그인 날은 제외** | 2건 | 두 표 `JOIN`, 시각 빼기(분 차이) |
| ④ | 시각 어긋남(퇴근) | 마지막 기록 시각과 수기 퇴근의 차이가 **10분 이상**. **퇴근 미태그인 날은 제외** | 1건 | 〃 |

- 합계 **12건**
- 기준 10분은 `checks.py` 맨 위 `TIME_DIFF_MINUTES` 한 곳에서만 정한다.
- 미태그인 날을 시각 어긋남에서 빼는 이유: **같은 문제를 두 번 세지 않기 위해서.** 원인(미태그)으로 한 번만 보여주고, 시간 차이는 그 줄의 상세에 적는다. (사용자가 W5에서 퇴근 미태그 오탐을 고친 경험과 같은 종류의 문제)

### 찾은 결과의 모양 (모든 규칙이 같은 모양으로 돌려줌)

필드: **종류 / 직원 / 날짜 / 상세**. 테스트는 **(종류, 직원, 날짜)** 가 정답 목록과 정확히 같은지 비교한다. 상세 문구는 비교하지 않는다.

| 종류 | 직원 | 날짜 | 상세 (예시 — 실제 시각은 seed가 정함) |
|---|---|---|---|
| 중복 기록 | E003 | 2026-09-03 | IN 08:01 이 2번 |
| 기록 없음 | E004 | 2026-09-04 | 수기 08:00~17:00, 단말 기록 0건 |
| 출근 미태그 | E003 | 2026-09-08 | 출근 등록 12:01(첫 기록) / 수기 08:00 → 4시간 1분 늦게 잡힘 |
| 퇴근 미태그 | E002 | 2026-09-02 | 퇴근 등록 15:11(마지막 기록) / 수기 17:00 → 1시간 49분 짧게 잡힘 |
| 시각 어긋남(출근) | E001 | 2026-09-01 | 단말 08:40 / 수기 08:00 (40분) |
| 시각 어긋남(퇴근) | E006 | 2026-09-08 | 단말 16:15 / 수기 17:00 (45분) |

**첫 버전에 안 넣는 것:** 날짜·직원 필터, 로그인, 화면에서 데이터 수정

- 앞선 목적 보충과 변경 이력의 소명 검토 추천·선택 대기 상태는 이 승인으로 대체된다. 기존 설계 3의 날짜·직원 필터 제외 결정은 AI 확장에 맞춰 범위를 다시 정한다.

### 첫 버전 조회 범위 (2026-10-01 · [Codex], 사용자 승인)

- 문제 목록 조회: 날짜·문제 종류로 찾기. 예: “9월 2일 퇴근 미태그 보여줘.”
- 직원별 기록 조회: 직원·날짜로 수기 시각과 출입 기록을 함께 보기. 예: “E002의 9월 2일 기록 보여줘.”
- 시간 차이 조건 조회: 날짜·출근/퇴근·차이(분)로 찾기. 예: “9월 1일 출근 시간이 30분 이상 차이 나는 직원 보여줘.”
- 예시 문장과 표현이 달라도 같은 뜻이면 처리하는 것을 목표로 한다. AI의 조건 해석 방식과 모호한 질문 처리·평가 기준은 다음 설계 조각에서 정한다.

### 질문을 SQL 조회에 연결하는 방식 (2026-10-01 · [Codex], 사용자 승인)

- 비교: AI가 질문마다 SQL 전체를 작성하는 방식은 자유도가 높지만 생성 SQL의 정확성을 따로 검증해야 한다. AI는 조건만 추출하고 앱이 미리 작성한 SQL을 실행하는 방식은 지원 범위가 명확하고 테스트하기 쉽다.
- 추천: AI가 조회 종류·날짜·직원·문제 종류·시간 차이 조건을 추출 → 앱이 조건을 검증 → 미리 작성한 SQL에 값을 전달 → DB 조회 결과와 근거 기록을 표시한다.
- 예: “9월 1일 출근 시간이 30분 이상 차이 나는 직원” → 날짜 2026-09-01(현재 데모 기간 기준), 종류 출근 시각 어긋남, 시간 차이 30분 이상. 기존 이상 판정 기준 10분을 바꾸는 것이 아니라 조회 조건으로 결과를 좁힌다.
- SQL은 값을 매개변수로 받아 조회한다. AI가 만든 SQL 문자열을 직접 실행하는 방식은 이 추천안에 포함하지 않는다. 조건이 모호하거나 지원 범위 밖일 때의 동작은 다음 조각에서 정한다.

### AI 확장 승인 이력

- **2026-10-01 · [Codex]:** 사용자가 첫 버전 조회 범위 세 가지(문제 기록·직원별 기록·시간 차이 조건)를 승인함. 질문 해석과 SQL 실행 연결 방식은 제안 단계임.
- **2026-10-01 · [Codex]:** 사용자가 AI 조건 추출 → 앱의 조건 검증 → 미리 작성한 SQL 실행 → 실제 DB 결과 표시 방식을 승인함.

### 생략·모호한 질문과 조회 결과 처리 (2026-10-01 · [Codex], 사용자 승인)

- 날짜를 생략하면 데모 전체 기간(2026-09-01~2026-09-14), 직원을 생략하면 전체 직원을 대상으로 한다. 화면에 실제 적용한 조회 조건을 함께 표시한다.
- 뜻이 모호하거나 현재 지원하지 않는 질문이면 임의의 조건으로 조회하지 않고 가능한 조회 범위를 안내하며 한 가지 확인 질문을 한다. 예: “늦게 온 직원”은 수기보다 첫 단말 기록이 늦은 경우를 뜻하는지 확인한다. 실제 지각 사실을 단말 기록만으로 단정하지 않는다.
- 조회가 정상 실행됐지만 조건에 맞는 결과가 없으면 “해당 조건의 기록이 없습니다”라고 표시한다. DB/API 오류나 데모 데이터 기간 밖 요청을 결과 0건과 섞지 않고 각각 실패·보유 기간을 안내한다.
- **2026-10-01 · [Codex]:** 사용자가 생략 조건의 기본값 표시, 모호한 질문 재확인, 결과 없음·보유 기간 밖·실행 실패의 구분을 승인함. 다음은 AI 평가 기준과 모델/API 선택이다.

### AI 평가 방법 제안 (2026-10-01 · [Codex], 아직 승인 전)

> **2026-10-01 · [Codex] 이해 확인:** 사용자가 “테스트를 해보자는 거지?”라고 정리한 뒤 이해했다고 답함. 정답을 아는 질문으로 예상 결과를 확인한다는 원칙에 동의한 것으로 기록한다. 아래 20문항·3회 등 상세 수치는 아직 확정하지 않는다.

- 질문 20개와 사람이 작성한 기대 조회 조건·동작·결과를 준비한다. 세 가지 조회 유형, 같은 뜻의 다른 표현, 조건 생략, 모호한 질문, 결과 없음, 보유 기간 밖 요청을 포함한다.
- 평가 항목: AI가 날짜·직원·문제 종류·시간 차이를 올바르게 해석했는지, 필요한 경우 되물었는지, 앱이 기대 DB 결과를 보여줬는지 확인한다. 문장의 글자 일치보다 조건과 동작·조회 결과를 비교한다.
- 같은 20개 질문을 3회 실행하여 총 60회 결과를 기록하고, 조건 해석·동작·최종 조회 결과의 성공 건수와 실패 예시를 구분해 README에 공개한다. 이 수치는 해당 데모 평가셋 결과이며 일반적인 정확도로 확대하지 않는다.
- API/DB 실패는 별도 자동 테스트에서 실패를 재현해 안내 동작을 확인한다. AI의 잘못된 조건은 앱이 검증하고, 실제 DB 결과를 그대로 표시하는 원칙도 검사한다.
- 기존 SQL 이상 탐지 정답 12건 테스트와 AI 평가 20개 질문은 서로 다른 검증이다. 평가용 기대값을 모델 출력으로 생성하지 않는다.

### AI 연결 방법 제안 (2026-10-01 · [Codex], 아직 승인 전)

> **2026-10-01 · [Codex] 사용자 선호 추가:** 가능하면 자체 관리 서버에서 AI를 실행하고 싶다고 함. 따라서 아래 외부 API 추천은 채택되지 않았으며, 현재는 자체 실행의 가능성을 우선 검토한다. GPU는 필수가 아니지만 기존 t2.micro의 RAM 1 GiB로 실용적인 실행이 가능한지는 모델별 확인이 필요하다. 구체 모델·실행 도구·서버 사양·비용은 아직 미확정. Ollama는 OCR 모델이 아니라 모델 실행 도구라는 개념을 설명함.

- 외부 AI API를 호출하는 방식과 서버에서 모델을 직접 실행하는 방식을 비교한다. 첫 버전은 별도 모델 실행 환경 관리가 필요 없는 외부 API 방식을 추천한다.
- 후보: OpenAI API. Flask 앱이 사용자 질문을 보내고 날짜·직원·문제 종류 등 정해진 형태의 조건을 받아 기존 조회 흐름에 연결한다. 구체 모델·예산은 아직 미정이다.
- 공식 문서 확인: 정해진 형식의 응답 기능은 https://developers.openai.com/api/docs/guides/structured-outputs , 사용량 과금은 https://developers.openai.com/api/docs/pricing 를 참고했다. 출력 형식 보장이 의미의 정확성을 보장하는 것은 아니므로 앱의 조건 검증과 테스트를 유지한다.

### 자체 실행 모델 후보 조사 (2026-10-03 · [Codex], 선택·설치 승인 전)

| 후보 | Ollama 배포 파일 크기 | 검토 목적 |
|---|---|---|
| Qwen3 1.7B (`qwen3:1.7b`) | 1.4GB | 작은 후보와 비교 |
| Qwen3 4B Instruct (`qwen3:4b-instruct`) | 2.5GB | 질문에서 조건을 추출하는 첫 시험 후보로 제안 |
| Gemma 3 4B (`gemma3:4b`) | 3.3GB | 다른 모델 계열의 비교 후보 |

- 위 숫자는 다운로드 파일 크기다. 실행 시에는 모델 외에 질문 처리용 메모리와 운영체제·앱 메모리도 필요하다. 필요한 RAM·속도·한국어 질문 해석 품질은 아직 실측하지 않았다.
- 기존 AWS t2.micro는 공식 사양상 1 vCPU·RAM 1 GiB로 위 후보의 실행 환경으로 추천하지 않는다.
- 실행 장소 비교: ① PC 사양을 확인한 뒤 먼저 시험하고 AWS 사양을 결정(추천, PC가 꺼지면 서비스도 중단되므로 상시 배포는 별도 결정) ② 처음부터 더 큰 AWS 인스턴스를 검토(서버에서 바로 실습 가능, 사양·비용 확인 필요).
- 우선 후보 제안은 Qwen3 4B Instruct이며, 성능 우위를 실측한 결론은 아니다. PC 사양이 부족하면 후보와 실행 장소를 다시 검토한다. 모델·서버·비용·설치는 사용자 승인 전이다.
- 출처: [Qwen3 배포 목록](https://registry.ollama.com/library/qwen3/tags), [Qwen3 4B Instruct](https://ollama.com/library/qwen3:4b-instruct), [Gemma 3 배포 목록](https://registry.ollama.com/library/gemma3/tags), [Ollama 메모리·실행 FAQ](https://docs.ollama.com/faq), [AWS T2 사양](https://aws.amazon.com/ec2/instance-types/t2/).

### WSL 메모리 확인·시험 구성 제안 (2026-10-03 · [Codex], 구성 승인 전)

- 사용자가 공유한 `free -h`: total 7.5GiB, used 630MiB, free 6.8GiB, available 6.9GiB. Swap total 2.0GiB, used 0B. Windows와 같은 물리 RAM을 사용하므로 WSL의 available 수치를 호스트와 독립된 여유 RAM으로 보지 않는다.
- 첫 시험 제안: 기존 WSL Ubuntu에 Ollama를 설치해 `qwen3:4b-instruct`를 CPU로 실행. 짧은 질문을 한 번에 하나씩 처리하고, 우선 날짜·문제 종류 추출과 응답 시간·메모리 사용량을 확인한다. 실행 시 질문 처리 길이는 작게 제한할 계획이며 구체 설정은 설치 전 정한다.
- 시험 예: 데모 연도 2026년이라는 지시와 함께 “9월 2일 퇴근 미태그 보여줘” → 날짜 2026-09-02·종류 퇴근 미태그. 아직 앱/DB와 연결하지 않고 모델의 조건 추출만 확인한다.
- 이 시험의 성공은 전체 앱 정확도나 다른 한국어 질문의 성공을 보장하지 않는다. 성능·자원 사용이 부적합하면 작은 후보(Qwen3 1.7B 등)를 비교한다. 시험 구성은 아직 사용자 승인 전이며 설치하지 않았다.
- 참고: [WSL 메모리 설정](https://learn.microsoft.com/en-us/windows/wsl/wsl-config), [Qwen3 4B Instruct 배포 정보](https://ollama.com/library/qwen3:4b-instruct).

### 시험 구성 승인·설치 단계 (2026-10-03 · [Codex], 사용자 승인)

- 사용자가 WSL Ubuntu + Ollama + Qwen3 4B Instruct의 CPU 시험을 승인함. 기존 앱 폴더·코드 생성 없이 모델 실행 가능성과 짧은 근태 조건 추출을 먼저 시험한다.
- 사전 확인: `ollama` 명령 검색 결과 없음, curl 있음, 아키텍처 x86_64, systemd 실행 중. 설치는 사용자가 직접 타이핑한다.
- 첫 단계: [Ollama 공식 Linux 설치 안내](https://docs.ollama.com/linux)의 `curl -fsSL https://ollama.com/install.sh | sh` 실행. 설치 출력 확인 후 다음 명령을 안내한다. 에이전트는 설치를 대신 실행하지 않았으며, 아직 설치 성공 증거가 없다.

- 실행 상태: 앱 완성 후 공식 평가를 진행할 계획이며 아직 실행 전. 현재 8개 질문·기대값 설계 표와 초기 네 번의 실행 시험 기록이 존재함. 승인 자체를 공식 24회 결과나 모델의 최종 품질 검증으로 취급하지 않음.
- 다음 설계 조각: 세 가지 조회 유형과 되묻기를 지원하는 AI 출력 형식·공통 지시. 모델 최종 채택·서버·비용·배포·구현 순서는 이어서 확정함.

### AI 출력 형식·공통 지시 (2026-10-05 · [Codex], 사용자 승인 대기)

**방식 비교와 추천**

| 방식 | 특징 |
|---|---|
| 자유 문장 | 사람이 읽기 편하지만 앱에서 필요한 항목을 다시 분리해야 함 |
| JSON 고정 양식(추천) | 항목 이름과 값의 종류를 정해 앱이 읽고 누락·잘못된 값을 검사하기 쉬움 |

사용자는 웹 화면에서 짧은 질문만 입력함. 앱이 공통 지시와 필요한 데모 정보를 붙여 Ollama에 보내며, 사용자가 매번 긴 지시를 입력할 필요는 없음. JSON은 앱이 받는 내부 응답이고 화면에는 조회 결과와 적용 조건을 보여줌.

**고정 항목 9개**

| 항목 | 의미·허용 값 |
|---|---|
| action | query(조회), clarify(뜻 확인), unsupported(지원 범위 안내) |
| query_type | issues(문제 목록), employee_records(직원 기록), time_difference(시간 차이), 또는 null |
| date_from | 시작 날짜 YYYY-MM-DD, 날짜 생략 시 null |
| date_to | 끝 날짜 YYYY-MM-DD, 날짜 생략 시 null. 하루 질문은 시작과 같은 날짜 |
| employee_id | 질문에 지정된 직원 번호 또는 null. null은 직원 조건 생략 |
| issue_type | 중복 기록, 기록 없음, 출근 미태그, 퇴근 미태그, 시각 어긋남(출근), 시각 어긋남(퇴근), 또는 null |
| time_side | 시간 차이 조회의 출근 또는 퇴근, 해당 조건이 없으면 null |
| min_difference_minutes | 시간 차이의 '몇 분 이상' 조건을 정수로 표시. 해당 조건이 없으면 null |
| question | 뜻 확인·지원 범위 안내 때 사용자에게 물을 한 가지 질문. 조회할 때는 null |

모든 항목 이름은 항상 포함하고 사용하지 않는 값은 null로 둠. null은 지정된 값이 없다는 뜻이며, 의미를 알 수 없는 질문을 임의로 null 처리해 전체 조회하지 않음.

**설명용 기대 응답 — 실제 모델 실행 결과 아님**

질문: “9월 2일 퇴근 미태그 보여줘.”

```json
{
  "action": "query",
  "query_type": "issues",
  "date_from": "2026-09-02",
  "date_to": "2026-09-02",
  "employee_id": null,
  "issue_type": "퇴근 미태그",
  "time_side": null,
  "min_difference_minutes": null,
  "question": null
}
```

**공통 지시 초안**

1. 근태 질문을 문제 목록·직원별 기록·시간 차이의 세 조회 유형으로 해석하고 위 JSON 객체 하나로 응답한다. 설명 문장이나 코드 블록은 붙이지 않는다.
2. 질문에서 날짜·직원·문제 종류·시간 차이 조건을 추출한다. 데모 연도는 2026년이다. 출근·퇴근을 안 찍었다는 표현은 각각 출근·퇴근 미태그로 해석한다. 문제 종류는 지정한 여섯 이름 전체를 사용한다.
3. 날짜를 생략하면 날짜 두 항목을 null, 직원을 생략하면 employee_id를 null로 둔다. 앱이 날짜 생략 시 전체 데모 기간, 직원 생략 시 전체 직원을 적용하고 표시한다. 문제 목록 전체를 요청하면 issue_type은 null이다.
4. 날짜를 명시했으면 보유 기간 밖이더라도 그 날짜를 그대로 전달한다. 보유 기간으로 바꾸지 않는다. 직원 이름을 번호로 바꿀 때는 앱이 제공한 가짜 직원 목록으로만 연결한다. 모르는 직원이나 불명확한 날짜·뜻은 확인한다.
5. '늦게 온 직원'처럼 뜻이 불명확하면 action을 clarify로 하고 question에 짧은 확인 질문 하나를 넣는다. 지원하지 않는 요청은 unsupported와 지원하는 조회로 이어질 한 가지 질문을 돌려준다. 이 두 경우에는 조회를 실행하지 않는다.
6. 시간 차이 조회는 출근/퇴근과 '몇 분 이상' 조건을 추출한다. 출근인지 퇴근인지 불명확하면 확인한다. 초과·이하 등 다른 비교 의미를 임의로 '이상'으로 바꾸지 않고 확인한다. 기존 SQL의 이상 판정 기준 10분은 조회 필터와 구분한다.
7. 직원 검색 결과·시각·출입 기록·SQL은 생성하지 않는다. 조회 결과는 앱이 실제 DB에서 가져온다.

**앱이 담당할 검증과 처리**

- JSON 형식·항목·허용 값, 실제 날짜와 기간 순서, 직원 존재 여부, 시간 차이 값과 조회 유형의 조합을 확인한다. action이 query일 때 query_type이 필요하며, 시간 차이 조회에는 time_side와 min_difference_minutes가 필요하다. 직원 기록 조회에는 문제 종류·시간 차이 필터를 섞지 않는다.
- clarify 또는 unsupported이면 조회를 보류하고 확인 질문을 표시한다. unsupported에는 지원 조회 범위도 안내한다. 유효하지 않은 응답이나 실행 오류는 조회 결과 0건으로 처리하지 않는다.
- 날짜 두 값이 생략됐으면 전체 데모 기간을 적용한다. 명시한 날짜가 범위 밖이면 보유 기간을 안내한다. 유효한 query만 미리 작성한 SQL에 값을 전달한다. 조건에 맞는 행이 없으면 정상 조회의 결과 없음으로 표시한다.
- AI에 요청하는 양식 제한과 앱의 검증을 함께 사용한다. [Ollama 공식 Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs)의 API format에 JSON Schema를 지정하는 방식을 활용한다. 형식 준수와 질문 의미의 정확성은 별도이므로 승인한 평가 기준으로 의미·동작·조회 결과를 검증한다.

승인 대기 범위는 위 JSON 양식·공통 지시·앱 처리 규칙이다. 양식은 검토용 설계이며 실제 모델 출력이나 앱 코드가 아니다. 다음 묶음은 모델·실행 장소·서버 사양·비용이다.
