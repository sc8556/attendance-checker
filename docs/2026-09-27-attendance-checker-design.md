# 근태 점검 설계 기록

앱을 만들면서 정한 것을 순서대로 적은 기록. 처음에는 AI 도구와 나눈 설계 대화를 그대로 쌓은 문서였고, 2026-11-17에 공개용으로 결정과 근거만 남겨 다시 씀. 날짜는 그 결정을 한 날.

MCP 서버 설계는 [`2026-11-09-mcp-design.md`](2026-11-09-mcp-design.md)에 따로 있음.

## 1. 목적과 범위

- 수기 근태 기록과 출입 단말 기록을 대조해 문제 기록을 찾는 작업을 가짜 데이터로 작게 재현함
- 새로 배우는 것: DB와 SQL(주력), Flask 템플릿, 자동 테스트
- 실제 데이터는 쓰지 않음. 코드를 공개 저장소에 올리기 때문
- 실제 도입이 아니라 역량을 보여 주는 시연이 목적

## 2. 큰 결정 (2026-09-24)

| 항목 | 결정 |
|---|---|
| 주제 | 근태 대조 미니 앱 |
| 찾을 문제 | 중복 기록, 기록 없음, 출근·퇴근 미태그, 시각 어긋남(출근·퇴근) |
| 데이터 입력 | 스크립트(`seed.py`)로 DB에 미리 넣음. CSV 업로드는 나중 후보 |
| 기술 | Flask + SQLite. PostgreSQL과 docker-compose는 완성 후 바꿀 후보 |

## 3. 전체 구조 (2026-09-26)

### 파일마다 역할 하나

| 파일 | 하는 일 |
|---|---|
| `answers.py` | 심어 둘 정답 목록. 사람이 손으로 적음 |
| `seed.py` | 가짜 데이터 생성. 실행할 때마다 DB를 지우고 새로 만듦. 정상 데이터는 규칙적으로 만들고 `answers.py`의 정답을 심음 |
| `attendance.db` | SQLite DB 파일. `seed.py`가 만들고 Git에는 안 올림 |
| `checks.py` | 문제 기록을 찾는 SQL. 함수가 DB 연결을 받아서 씀. 기준값 `TIME_DIFF_MINUTES = 10` |
| `app.py`, `templates/` | 결과를 웹 화면으로 보여 줌 |
| `tests/` | 테스트용 DB를 새로 만들어 검사함 |
| `Dockerfile` | 이미지를 만들 때 `seed.py`도 실행해 DB를 넣음 |

### 흐름

```
answers.py (정답 목록, 손으로 적음)
    │                          │
seed.py ▶ attendance.db       tests/
 (매번 새로)     │                 │ 테스트용 DB를 새로 만들어
            checks.py ◀───────────┘ 「찾은 것 = 정답」인지 확인
                │
            app.py ▶ 웹 화면
```

### 셀프 리뷰로 더한 원칙

1. `seed.py`를 두 번 돌려도 데이터가 쌓이지 않게 매번 새로 만듦. 쌓이면 가짜 「중복 기록」이 생김
2. 정상 데이터는 기준(10분)을 넘을 수 없는 범위 안에서 규칙적으로 만듦. 제한 없는 무작위는 우연히 문제 기록을 만들어 테스트를 흔듦
3. 정답은 판정 규칙과 상관없이 손으로 적음. 규칙으로 정답을 계산하면 규칙이 틀려도 테스트가 통과함
4. Docker 이미지를 만들 때 `seed.py`를 실행해 DB를 넣음
5. `checks.py` 함수는 DB 연결을 받아서 씀. 앱은 진짜 DB, 테스트는 새 테스트용 DB를 넘김
6. SQL은 코드에 넣기 전에 `sqlite3`로 손으로 먼저 쳐 봄
7. `.gitignore`에 `*.csv`, `*.xlsx`를 넣어 실제 자료가 실수로 올라가는 것을 막음

검토했지만 그대로 둔 것: SQL을 `.sql` 파일로 분리(파일만 늘어남), 사번과 단말 ID 연결 표(첫 버전에는 과함, 확장 후보)

## 4. 데이터 (2026-09-26~27)

### 표 3개

`employees` (직원 목록)

| 컬럼 | 설명 | 예 |
|---|---|---|
| `emp_id` | 사번 | `E001` |
| `name` | 지어낸 이름 | `김민준` |

`terminal_logs` (출입 단말 기록)

| 컬럼 | 설명 | 예 |
|---|---|---|
| `id` | 줄 번호(자동) | `1` |
| `emp_id` | 사번 | `E001` |
| `work_date` | 날짜 | `2026-09-02` |
| `log_time` | 시각 | `08:02` |
| `direction` | `IN` 또는 `OUT` | `IN` |

`manual_sheet` (수기 근태 기록)

| 컬럼 | 설명 | 예 |
|---|---|---|
| `emp_id` | 사번 | `E001` |
| `work_date` | 날짜 | `2026-09-02` |
| `check_in` | 수기 출근 | `08:00` |
| `check_out` | 수기 퇴근 | `17:00` |

형식 규칙: 날짜는 `YYYY-MM-DD`, 시각은 항상 두 자리 `HH:MM`(예: `08:02`). SQLite는 날짜와 시각을 글자로 저장해서, 두 자리로 맞춰야 글자 비교(`MIN`, `MAX`)로도 순서가 맞음.

### 정상 데이터 규칙

| 항목 | 규칙 |
|---|---|
| 직원 | 처음 10명(E001~E010). 나중에 E011, E012를 문제 없는 정상 기록으로만 추가해 12명 |
| 날짜 | 평일 10일. 2026-09-01, 02, 03, 04, 07, 08, 09, 10, 11, 14 |
| 수기 기록 | 전원 매일 출근 `08:00`, 퇴근 `17:00`(점심, 휴식은 안 적음) |
| 단말, 모든 직원 매일 | `08:00 IN`(출근), `12:00 OUT`(점심), `13:00 IN`(복귀), `17:00 OUT`(퇴근) |
| 단말, 짝수 사번 추가 | 매일 `15:00 OUT`, `15:10 IN`(휴식) |
| 흔들림 | 단말 시각은 위 기준에서 ±0~3분 안에서만. 매번 같은 결과가 나오게 만듦 |

점심과 휴식 기록은 설계 중에 더함. 실제 출입 기록은 하루에도 여러 번 찍히기 때문.

## 5. 판정 규칙과 결과 화면 (2026-09-27)

### 출근과 퇴근을 정하는 기준

| | 등록되는 시각 |
|---|---|
| 출근 | 그날 첫 기록(IN이든 OUT이든) |
| 퇴근 | 그날 마지막 기록(IN이든 OUT이든) |

퇴근을 안 찍으면 마지막으로 찍은 시각이 퇴근이 되고, 출근을 안 찍으면 첫 기록이 출근이 됨. 그래서 미태그는 근무시간이 짧게 잡히는 문제로 이어짐. 이 기준을 반영하면서 출근 미태그를 더해 정답이 10건에서 12건이 됨.

### 판정 규칙 (만든 순서)

| 순서 | 종류 | 정의 | 정답 | 쓰는 SQL |
|---|---|---|---|---|
| ① | 중복 기록 | 같은 직원, 날짜, 시각, 방향 기록이 2개 이상 | 2건 | `GROUP BY`, `HAVING`, `COUNT` |
| ② | 기록 없음 | 수기 기록은 있는데 그날 단말 기록이 0건 | 2건 | `NOT EXISTS` |
| ③ | 출근 미태그 | 그날 첫 기록이 OUT | 2건 | 묶음별 첫 값과 마지막 값(`MIN`, `MAX`, 서브쿼리, `JOIN`) |
| ③ | 퇴근 미태그 | 그날 마지막 기록이 IN | 3건 | 같음 |
| ④ | 시각 어긋남(출근) | 첫 기록과 수기 출근의 차이가 10분 이상. 출근 미태그인 날은 제외 | 2건 | 두 표 `JOIN`, 분 차이 계산 |
| ④ | 시각 어긋남(퇴근) | 마지막 기록과 수기 퇴근의 차이가 10분 이상. 퇴근 미태그인 날은 제외 | 1건 | 같음 |

- 기준 10분은 `checks.py`의 `TIME_DIFF_MINUTES` 한 곳에서만 정함
- 미태그인 날을 시각 어긋남에서 빼는 이유: 같은 문제를 두 번 세지 않으려고. 원인(미태그)으로 한 번만 보여 주고 시간 차이는 그 줄의 상세에 적음

### 결과의 모양

모든 규칙이 「종류, 직원, 날짜, 상세」 같은 모양으로 돌려줌. 테스트는 (종류, 직원, 날짜)가 정답 목록과 정확히 같은지 비교하고 상세 문구는 비교하지 않음.

첫 버전에 넣지 않은 것: 날짜·직원 필터, 로그인, 화면에서 데이터 수정. 필터는 나중에 AI 자연어 조회(7장)로 들어감.

## 6. 검증 방법 (2026-10-01)

- 처음에는 SQL로 데이터를 직접 확인하고, 이후 자동 테스트로 비교함
- 테스트용 DB를 새로 만들어 표별 줄 수를 확인한 뒤, 규칙별 결과의 (종류, 직원, 날짜)를 `answers.py`와 비교함
- 빠진 것 0, 잘못 찾은 것 0, 중복 0이어야 통과. 총 12건이라는 건수만으로는 통과시키지 않음

## 7. AI 자연어 조회 (2026-10-01~05)

### 방향

- 말로 질문하면 AI가 조건을 뽑고, SQL 조회 결과에 근거해 직원, 시간 차이, 관련 출입 기록을 보여 줌
- 다른 후보(결과 설명문, 확인 요청 초안, 소명 내용 대조)도 검토했지만 자연어 조회만 택함
- 기존 정답 12건 검증은 그대로 유지함

### 첫 버전 조회 범위

| 조회 | 조건 | 예 |
|---|---|---|
| 문제 목록 | 날짜, 문제 종류 | 9월 2일 퇴근 미태그 보여줘 |
| 직원별 기록 | 직원, 날짜 | E002의 9월 2일 기록 보여줘 |
| 시간 차이 | 날짜, 출근·퇴근, 차이(분) | 9월 1일 출근 시간이 30분 이상 차이 나는 직원 보여줘 |

### 질문을 SQL에 잇는 방식

| 방식 | 특징 |
|---|---|
| AI가 SQL 전체를 씀 | 자유도는 높지만 만들어진 SQL이 맞는지 매번 따로 검증해야 함 |
| AI는 조건만 뽑고 앱이 미리 만든 SQL을 실행(택함) | 지원 범위가 분명하고 테스트하기 쉬움 |

- 흐름: AI가 조건을 뽑음 → 앱이 조건을 검사 → 미리 만든 SQL에 값을 넘김 → DB 결과와 근거 기록을 보여 줌
- SQL은 값을 매개변수로 받음. AI가 만든 SQL 문자열을 실행하지 않음
- 시간 차이 조회의 「30분 이상」은 조회 조건일 뿐이고, 판정 기준 10분을 바꾸지 않음

### 생략, 모호한 질문, 결과 없음

- 날짜를 생략하면 데이터 기간 전체(2026-09-01~09-14), 직원을 생략하면 전체 직원. 실제 적용한 조건을 화면에 함께 보여 줌
- 뜻이 모호하거나 지원하지 않는 질문은 임의로 조회하지 않고 확인 질문 하나를 함. 예: 「늦게 온 직원」은 수기보다 첫 단말 기록이 늦은 경우인지 확인함. 단말 기록만으로 지각이라고 단정하지 않음
- 조회는 됐는데 맞는 기록이 없으면 「해당 조건의 기록이 없음」. DB나 AI 호출 오류, 데이터 기간 밖 요청은 0건과 섞지 않고 각각 따로 안내함
- 나중에 바꾼 것(2026-10-09): 요청 기간이 데이터 기간과 일부만 겹치면 겹치는 날짜로 잘라 조회하고 그 사실을 표시함. 전혀 안 겹치면 그대로 기간 밖으로 안내함

### AI 응답 형식 (JSON 9개 항목)

자유 문장 대신 JSON 고정 양식을 택함. 앱이 항목을 읽고 빠진 값이나 잘못된 값을 검사하기 쉬움.

| 항목 | 뜻과 허용 값 |
|---|---|
| `action` | query(조회), clarify(뜻 확인), unsupported(지원 범위 안내) |
| `query_type` | issues, employee_records, time_difference 또는 null |
| `date_from` | 시작 날짜 YYYY-MM-DD. 생략하면 null |
| `date_to` | 끝 날짜 YYYY-MM-DD. 생략하면 null. 하루짜리 질문은 시작과 같은 날짜 |
| `employee_id` | 사번 또는 null |
| `issue_type` | 문제 종류 6개 중 하나 또는 null |
| `time_side` | 출근 또는 퇴근, 없으면 null |
| `min_difference_minutes` | 「몇 분 이상」의 정수, 없으면 null |
| `question` | 뜻 확인, 범위 안내 때 물을 질문 하나. 조회할 때는 null |

모든 항목을 항상 넣고 쓰지 않는 값은 null로 둠. 뜻을 모르는 질문을 null로 채워 전체 조회하지 않음.

AI에게 주는 공통 지시의 요점

1. JSON 객체 하나로만 답함. 설명 문장이나 코드 블록을 붙이지 않음
2. 데이터 연도는 2026년. 「출근·퇴근을 안 찍었다」는 출근·퇴근 미태그. 문제 종류는 정해 둔 이름 전체를 씀
3. 날짜를 말했으면 데이터 기간 밖이어도 그대로 넘김. 기간에 맞춰 바꾸지 않음
4. 뜻이 불분명하면 clarify, 지원하지 않으면 unsupported. 이때는 조회하지 않음
5. 「초과」, 「이하」처럼 다른 비교를 「이상」으로 바꾸지 않고 확인함
6. 직원 결과, 시각, 출입 기록, SQL을 만들어 내지 않음. 결과는 앱이 DB에서 가져옴

앱이 맡는 검사: JSON 형식과 허용 값, 실제 있는 날짜와 기간 순서, 직원 존재 여부, 조회 종류와 조건의 조합(시간 차이 조회에는 출근·퇴근과 분 조건이 필요, 직원별 기록에는 문제 종류 조건을 섞지 않음). Ollama의 Structured Outputs로 JSON Schema를 지정하지만, 형식이 맞는 것과 뜻이 맞는 것은 별개라서 앱 검사와 평가를 함께 씀.

## 9. 모델과 실행 장소 (2026-10-01~05)

### 외부 API 대신 직접 실행

- 처음에는 외부 AI API 방식을 검토함. 운영할 모델 환경이 필요 없음
- 근태 기록은 실제 업무라면 사내 데이터라서 질문이 밖으로 나가지 않도록 직접 실행하는 모델을 택함

### 모델 후보

| 후보 | 배포 파일 크기 | 검토 목적 |
|---|---|---|
| Qwen3 1.7B (`qwen3:1.7b`) | 1.4GB | 더 작은 후보 |
| Qwen3 4B Instruct (`qwen3:4b-instruct`) | 2.5GB | 첫 시험 후보 |
| Gemma 3 4B (`gemma3:4b`) | 3.3GB | 다른 계열 비교 후보 |

- Qwen3 4B Instruct로 먼저 시험했고, 8장의 손 시험을 거쳐 이 모델로 평가를 진행함
- 다른 후보와 같은 질문으로 비교하지는 않음. 가장 좋은 모델이 아니라 정해 둔 기준을 통과한 모델
- 실행 도구는 Ollama. GPU 없이 CPU로 돌고, 응답을 정해 둔 JSON 형식으로 받을 수 있음

### 실행 장소

- 노트북(WSL)에서 CPU로 먼저 시험함
- 상시 운영용으로 4 vCPU, RAM 8GB급 서버 한 대에 Flask, SQLite, Ollama를 함께 두는 구성을 검토함
- 실제로는 서버를 만들지 않고, 앱과 모델을 Docker 이미지 하나로 묶어 노트북에서 띄우고 Cloudflare Quick Tunnel로 공개함(README 「실행 방법」)
