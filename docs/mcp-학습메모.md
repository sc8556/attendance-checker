# MCP 학습 메모 (2026-11-09)

이 저장소에 MCP 서버를 붙이면서 정리한 이해 메모. 작성자가 다른 PC 에서 이어서 볼 때 읽는 용도. 코드 줄 번호는 2026-11-09 의 `mcp_server.py`(128줄) 기준.

## 1. MCP 가 뭔가

- MCP(Model Context Protocol)는 AI 도구가 바깥 프로그램의 기능을 「도구」로 부르게 하는 표준 연결 방식. 전원 콘센트 규격에 비유. 규격을 맞춰 두면 Claude Code, Claude Desktop 같은 어떤 AI 도구든 꽂아 씀
- 「읽기」만이 아니라 「기능」을 여는 것. 무엇을 열지는 서버를 만드는 쪽이 정함. 이 저장소는 조회 4개만 열었고 쓰기는 없음
- 파일이 아닌 것(DB, 웹 서비스, 다른 프로그램)에 닿기 위한 것. 파일은 AI 코딩 도구가 원래 읽을 수 있음

## 2. 이 저장소의 세 경로

| 경로 | 누가 묻나 | 어떻게 답하나 |
|---|---|---|
| 화면 | 사람이 웹 화면에서 누름 | 앱이 고정 SQL 로 조회해 표로 보여 줌 |
| 자연어 | 사람이 「9월 2일 퇴근 미태그 보여줘」라고 침 | 앱 안의 로컬 AI(Ollama)가 조건만 뽑고, 앱이 고정 SQL 로 조회 |
| MCP | AI 도구가 `find_issues(9/2, 퇴근 미태그)` 를 부름 | 앱이 같은 고정 SQL 로 조회해 AI 도구에 돌려줌 |

세 경로 모두 AI 는 SQL 을 쓰지 않음. 조건 검사는 `nl_query.ask()` 한 곳에서 함.

## 3. 저장소를 당겨와 Claude Code 에 묻는 것과 뭐가 다른가

| | 저장소 당겨와서 Claude Code 에 묻기 | MCP 도구로 묻기 |
|---|---|---|
| AI 가 하는 일 | 코드를 읽고 직접 SQL 이나 파이썬을 짜서 DB 파일을 엶 | 조건(9/2, 퇴근 미태그)만 골라 `find_issues` 를 부름 |
| 조회문을 쓰는 쪽 | AI 가 매번 새로 씀. 틀릴 수도, 너무 많이 읽을 수도, 바꿀 수도 있음 | 앱이 미리 만들어 테스트한 SQL 하나. AI 는 SQL 을 못 씀 |
| 기간 밖 질문(10/1) | AI 가 0건이라고 할 수도 있음 | 앱이 「기간 밖」이라고 돌려줌(웹 화면과 같은 검사) |
| 자료가 다른 서버 DB 에 있으면 | 당겨올 수 없음. 폴더에 없는 자료는 못 봄 | MCP 서버가 자료 있는 쪽에서 돌며 창구만 열어 줌 |
| 개발 도구가 없는 사람 | Claude Code 와 터미널이 있어야 함 | Claude Desktop 에서도 같은 도구를 씀 |
| AI 의 권한 | 폴더 전체 읽기, 명령 실행 | 읽기 전용 도구 4개뿐 |

솔직한 정리: 가짜 DB 파일이 코드 옆에 있고 묻는 사람이 Claude Code 를 쓸 줄 알면, AI 가 직접 SQL 을 짜도 같은 답이 나옴. 이 시연은 「필요해서」가 아니라 「방식을 보여 주려고」 만든 것. 차이가 커지는 건 자료가 서버 DB 에 있고, 묻는 사람이 현업 담당자이고, AI 가 자료를 잘못 읽거나 바꾸면 안 되는 운영 상황.

## 4. 실무에서 MCP 를 왜 만드나

| 이유 | 뜻 | 예 |
|---|---|---|
| 연결 표준화 | AI 도구 5개 × 시스템 10개를 50번 따로 붙이지 않고, 시스템마다 MCP 서버 하나만 만들면 어떤 AI 도구든 꽂아 씀 | 노션 MCP 하나를 여러 AI 도구가 같이 씀 |
| 파일이 아닌 것에 닿기 | DB, 사내 시스템, 웹 서비스는 파일처럼 읽을 수 없어서 창구가 필요함 | 출입 기록 DB, 전자결재, 재고 시스템 |
| 접근 범위 통제 | 접속 정보는 서버가 쥐고, AI 에는 정해진 도구만 보여 줌. 읽기 전용, 행 수 제한, 위험한 동작은 승인 필요로 분리 | 이 저장소: 조회 4개, 쓰기 없음 |
| 개발 도구 없는 사람도 | 터미널 없이 채팅 화면만 있는 사람도 같은 기능을 씀 | 현업 담당자가 Claude Desktop 에서 질문 |
| 일관성과 기록 | 검증 로직이 한 곳에 있어 결과가 같고, 누가 무엇을 조회했는지 서버에 남음 | 기간 밖이면 언제나 같은 안내 |

주의: MCP 를 썼다고 자동으로 안전해지는 건 아님. 서버가 쓰기·삭제 도구를 열어 두거나 입력 검증을 안 하면 그대로 위험하고, 남이 만든 MCP 서버를 설치하는 것은 모르는 프로그램에 자료 접근을 주는 일. 「MCP 는 통제를 가능하게 하는 틀이고, 안전한지는 서버를 어떻게 만들었느냐에 달렸다」.

한 줄: MCP 는 AI 도구와 시스템을 잇는 표준 콘센트. 한 번 만들면 어떤 AI 도구든 쓰고, 무엇을 열어 줄지 좁히는 것으로 접근을 통제함.

## 5. 실무에서 어떻게 만드나

- 셋 중 하나. 이미 있는 서버를 설치만 함(노션, 깃허브, 구글 시트 등) / AI 코딩 도구로 만들고 사람이 설계·검증(이 저장소가 이 경우) / 손으로 짬(로그인 연동, 원격 HTTP, 코드 리뷰가 엄격한 곳)
- MCP 서버 코드는 대부분 이미 있는 DB 나 API 를 감싸는 얇은 껍데기라 길어야 몇백 줄. 어려운 부분은 코드가 아니라 결정
- 어떻게 만들든 사람이 반드시 하는 네 가지
  1. 설계: 어떤 도구를 열고 무엇을 안 열지, 인자는 무엇인지, 쓰기를 허용할지
  2. 코드 전부 읽기: 작은 서버는 30분
  3. 검증은 두 겹: AI 가 짠 테스트만 믿지 않고 사람이 따로 적은 정답(`answers.py` 12건)과 대조, 실제 클라이언트(Claude Code)로 「해서는 안 되는 요청」(지워 줘, 기간 밖 보여 줘)을 넣어 거절되는지 확인
  4. 운영 자료에 붙일 땐 다른 사람이 한 번 더 읽고, 읽기 전용 계정으로 돌림

읽을 때 체크리스트

| 볼 곳 | 확인할 것 | 이 저장소에서는 |
|---|---|---|
| 연결 여는 부분 | 읽기 전용인가, 접속 정보가 코드에 박혀 있지 않은가 | SQLite `mode=ro`, 비밀번호 없음 |
| 인자 검증 | 날짜·ID·종류를 검사하나, 검사를 한 곳에서 하나 | `nl_query.ask()` 재사용 |
| 결과 크기 | 한 번에 다 퍼 주지 않나 | 500행 상한 |
| 오류 처리 | 실패가 예외로 터지지 않고 AI 가 읽을 수 있는 상태로 돌아오나 | `status`(기간 밖, 없는 직원) |
| 도구 설명문 | AI 가 잘못 고르지 않게 용도가 분명한가 | 도구별 한국어 설명 |

## 6. mcp_server.py 읽는 법

| 줄 | 무엇 | 읽는 법 |
|---|---|---|
| 1~8 | 머리말 | 이 파일이 뭘 하는지 한국어 설명. 여기만 읽어도 절반은 이해됨 |
| 10~23 | 가져오기 | 다른 파일의 기능을 빌려 옴. `nl_query`(조건 검사), `seed`(가짜 DB), `checks`(판정 SQL) |
| 25~36 | 설정 | 25줄 `MAX_ROWS = 500` 행 수 상한. 27줄 읽기 전용 표시. 29~36줄 서버 이름과 AI 에게 보이는 안내문 |
| 39~65 | 공통 함수 2개 | `connect()` 읽기 전용으로 DB 열기, `run()` 조건을 JSON 으로 만들어 `nl_query.ask()` 에 넘기고 결과 정리 |
| 68~124 | 도구 4개 | `＠server.tool` 이 붙은 함수가 곧 도구. 바로 밑 따옴표 글이 AI 가 읽는 사용 설명서 |
| 127~128 | 시작 | 실행하면 서버가 켜져 기다림 |

예시: 「9월 2일 퇴근 미태그 보여줘」가 지나가는 길
1. AI 가 70~72줄 설명을 읽고 `data_range` 를 먼저 부름. 75~82줄이 기간, 직원, 문제 종류 목록을 돌려줌
2. AI 가 `find_issues(date_from="2026-09-02", date_to="2026-09-02", issue_type="퇴근 미태그")` 를 부름. 98줄에서 `run("issues", …)` 로 넘김
3. `run`(47줄): 49~51줄에서 조건을 JSON 으로 만듦. 52줄 `connect()` 로 DB 를 염(44줄 `mode=ro` 가 읽기 전용). 54줄 `nl_query.ask()` 가 날짜, 직원, 종류를 검사하고 고정 SQL 로 조회. 57~65줄에서 결과를 정리하고 64줄에서 500행까지만 자름
4. 돌아가는 것: `status: "ok"`, `total: 1`, `rows: [E002, 2026-09-02, 퇴근 미태그 …]`

읽으면서 확인할 세 줄
- 44줄: `?mode=ro` 가 있는가. 있으면 어떤 도구도 데이터를 못 바꿈
- 54줄: 검사를 여기서 직접 하지 않고 `nl_query.ask()` 에 넘기는가. 화면과 같은 검사를 한 곳에서 함
- 64줄: `[:MAX_ROWS]` 가 있는가. 한 번에 다 퍼 주지 않음

손으로 만져 보기(5분): 25줄 `500` 을 `0` 으로 바꾸고 `uv run pytest -q` 를 돌리면 테스트가 깨짐. 다시 `500` 으로 되돌리면 79개 통과. 한 번 해 보면 「이 코드를 안다」고 말할 수 있음.

## 7. ToolAnnotations 가 뭔가

도구에 붙이는 「성격 표시 딱지」. 코드가 하는 일을 바꾸지 않고, AI 도구에게 「이 도구는 이런 성격이다」라고 알려 주기만 함. 27줄을 풀면 아래와 같고, `READ_ONLY` 라는 이름으로 한 번 만들어 도구 4개에 전부 붙임(68, 86, 101, 112줄).

| 표시 | 값 | 뜻 |
|---|---|---|
| `read_only_hint=True` | 읽기만 함 | 데이터를 바꾸지 않는 도구 |
| `destructive_hint=False` | 파괴 아님 | 지우거나 덮어쓰지 않음 |
| `idempotent_hint=True` | 여러 번 불러도 같음 | 두 번 불러도 결과와 상태가 안 변함 |
| `open_world_hint=False` | 바깥 안 나감 | 인터넷 같은 외부로 안 나가고 이 DB 안에서만 |

- 왜 붙이나: AI 도구가 이 딱지를 보고 「읽기 전용이니 사용자에게 매번 확인을 안 받아도 되겠다」처럼 판단할 수 있음. 딱지가 없거나 파괴로 표시되면 부를 때마다 허락을 묻는 쪽으로 기움
- 주의: 이건 힌트, 즉 자기 신고. 딱지에 읽기 전용이라 적어도 코드가 실제로 지우면 지워짐. 진짜 보호는 44줄 `mode=ro` 이고 27줄은 그 사실을 알려 주는 안내문. 한 줄로 「44줄이 자물쇠, 27줄이 자물쇠가 있다는 안내판」

## 8. 미리 알아야 하는 것과 찾아보면 되는 것

| 미리 알아야 하는 것 | 찾아보면 되는 것 |
|---|---|
| 이 서버가 뭘 열어 주고 뭘 막는지 | `ToolAnnotations` 같은 라이브러리 이름과 옵션 |
| 진짜 보호(44줄)와 안내판(27줄)의 차이 | 각 옵션의 정확한 철자와 기본값 |
| 검사를 한 곳에서 하는 이유 | SDK 가 stdio 로 통신하는 방식 |
| 테스트가 무엇을 증명하고 무엇을 못 하는지 | 파이썬 문법 세부 |

개발자도 왼쪽은 머리에 있고 오른쪽은 문서를 봄. 모르는 이름이 나오면 숨기지 말고 「SDK 옵션은 문서 보고 썼고, 뜻은 AI 도구에게 읽기 전용이라고 알려 주는 표시, 실제 보호는 DB 를 읽기 전용으로 연 부분」처럼 답하면 됨.

## 9. 요즘 개발 순서

1. 무엇을 만들지 정하고 지시(범위, 하지 말 것, 완료 기준)
2. AI 가 코드를 씀
3. 사람이 읽음. 모르는 이름은 찾아봄(문서, 검색, 또는 AI 에게 묻고 문서로 한 번 더 확인)
4. 검증. 테스트 돌리기, 직접 써 보기, 「하면 안 되는 것」을 시켜서 막히는지 보기
5. 틀리면 고치라고 지시하고 3~4 반복

달라지는 점 세 가지
- 읽기만으로는 부족하고 깨뜨려 봐야 함(6절 끝)
- AI 가 짠 테스트만 믿지 않고 사람이 정답을 따로 적어 둠(`answers.py`)
- 코드가 크면 다 안 읽고 위험한 곳부터 읽음. 데이터를 바꾸는 곳, 권한과 접속 정보, 외부로 나가는 곳. 운영에 붙일 땐 다른 사람이 한 번 더 읽음

숙련 개발자와의 차이는 「어디를 먼저 볼지」 아는 속도이지 과정이 다르지 않음. 직접 짜지 않은 것은 약점이 아니고, 읽지 않은 것이 약점.

## 10. 이 저장소를 설명할 때 답할 말

- MCP 가 뭐냐: 2절 표의 MCP 줄. 같은 판정을 AI 도구가 정해진 창구로만 부르게 한 것
- 저장소를 당겨와 묻는 것과 차이: 시연에서는 차이가 작음. 차이는 SQL 을 누가 쓰느냐. 운영에서는 AI 가 SQL 을 쓰지 않고 검증된 조회만 부르게 해야 하고 그 창구를 표준으로 만든 것이 MCP
- AI 가 만든 코드를 어떻게 검증했나: 손으로 적은 정답 12건과 한 건씩 대조하는 테스트, 기간 밖·없는 직원 같은 거절 케이스 8가지, 읽기 전용이 실제로 걸리는지 확인하는 테스트, 코드를 전부 읽고 한 군데 바꿔 테스트가 깨지는 것을 확인
- 직접 짜지 않았는데 괜찮나: 구현은 AI 코딩 에이전트에 위임하고, 도구 범위·읽기 전용·검증 방식은 작성자가 정함. 코드는 전부 읽음
